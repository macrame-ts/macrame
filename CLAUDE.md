# Task System

## Project

Open-source C++ task/scheduler system, generic but game-engine-focused. Inspired by Unreal Engine's Tasks System (which the author designed and implemented at Epic Games), with improvements and additional functionality. Goals: UX, performance, rich functionality.

## Author

Experienced engine programmer. Designed and implemented UE Tasks System at Epic Games. Expects expert-level C++ discussion — no hand-holding, no over-explaining idioms.

## Stack

- C++23 (MSVC/clang-cl on Windows, Visual Studio solution)
- No external dependencies
- Lock-free/low-contention concurrency preferred

## Current State

Four layers, all built and tested (the harness suite, the sample, and the benchmarks all pass). Sources: core at repo root, plus `tests/`, `benchmarks/`, `sample/`.

- **`Scheduler`** (`scheduler.{h,cpp}`, `worker_thread.{h,cpp}`) — priority queue + `std::jthread` worker pool. `Priority {high, normal, low}` (in `priority.h`, shared with the task core) orders the queue; every queued task route threads a priority to `submit`: `ts::launch(fn, {.priority=p})`, `ts::task(fn).priority(p)`, `Guarded::async(fn, {.priority=p})`, `Graph_node::priority(p)` — stored on the block, applied at dispatch (incl. prerequisite-gated). Per-instance `Idle_policy` via `Scheduler_config` at construction (runtime enum, no measurable hot-path cost), three modes: `spin` = never park, yield-loop (producers never signal); `spin_then_block` (**default**, UE-style) = spin `spin_cycles` scans on the `Event_count` (eventcount, not a semaphore) before parking, producer wakes one per submit (`spin_cycles == 0` degenerates to park-immediately); `handoff` = Go-style spinner handoff (a spinner that finds work promotes a successor before running; producer issues the wake syscall only on the fully-parked 0→1 transition, else a cheap epoch bump — moves wake cost off the producer). Wake latency ~40% lower than a bare park; throughput cost on uncontended streams. See `signal_submit`/`handoff_wait` in `scheduler.cpp`. Runtime, not templated — the `thread_local Scheduler* current_scheduler` rules out templating `Scheduler`. The single mutex-guarded `std::priority_queue` is the known scaling bottleneck (benchmarks confirm).
- **`Guarded<T>`** (`guarded.{h,cpp}`) — the access-controlled wrapper; the only sanctioned way to touch a thread-unsafe `T` across threads. `async(fn, opts={})` runs `fn(T&)` (write) or `fn(const T&)` (read) on a per-object **reader/writer pipe** (concurrent readers, exclusive writer, FIFO, non-blocking completion-driven dispatch). Access mode is deduced from the functor's parameter const-ness. A `Task_options` aggregate (shared with `then`; defined in `task.h`) carries `{.token, .priority, .run_inline}`; `run_inline` runs the body **synchronously on the calling thread** when the pipe is immediately free (`pipe_try_inline` — reader joins as a reader, writer as an exclusive writer; never jumps queued work), else it enqueues as usual — so it blocks the caller and stacks the access scope (don't opt in from inside a graph node). Constructs `T` in place; adopting an existing instance is future work. **Multi-object async**: the free function `ts::async(fn, objs...)` (options first: `ts::async({.priority=p}, fn, objs...)`) runs `fn(*obj1, *obj2, ...)` over several `Guarded`s at once — per-arg mode from const-ness (`Function_traits`), acquiring each object's pipe mode-aware in **canonical (pipe-address) order, holding** (`multi_acquire`, the same `pipe_acquire`/`pipe_release` primitive as the graph — shared address order, so nodes and multi-object asyncs can't deadlock), running under an `Access_context` declaring all, then releasing at completion (`attach`). Deadlock-free by ordered acquisition; dedups a repeated object (write-wins).
- **`Task<R>`** (`task.h`) — async result handle, the single representation for every result-bearing producer (`async`/`then`/`when_all`/`execute`): `sync()` (call once), `is_done()`, `then(fn, opts={})` (continuation — a **proper scheduled task** with the producer as a `num_locks` prerequisite, queued by default so it gets a priority and the scheduler can interleave; a `Task_options` aggregate carries `{.token, .priority, .run_inline}` so a `then` dispatches inline / at a priority / with its own cancel token, same as a builder task). `ts::launch`/`ts::nested` take a `Launch_options{.token, .priority}` (no `run_inline` — a bare task has no settling thread; inline is a builder capability). `when_all(tasks...)` joins typed prerequisites into `Task<tuple<...>>` — void prerequisites are pure ordering and drop out (all-void → `Task<void>`); non-void results are moved into the tuple (move-only supported); consume via `then([](tuple&){...})` or apply-style `then([](A& a, B& b){...})`. `Task` is a completion handle only — it does not carry graph identity (see `Graph_node`). The shared state is a **fully monomorphic** `detail::Task_control_block` (not templated at all — the result is erased behind `void* result_ptr` and composed via a `Result_block<R>` wrapper the handle `shared_ptr`-aliases; no `<void>` specialization; no virtual dispatch). The **body** lives in the block too: `async` and `ts::launch(fn)` (standalone, no access target) store it in an `Executable<Body,R>` wrapper reached via a `core.execute` fn-ptr (body type erased, block stays monomorphic). **Prerequisites** via the block's lock-counter (`num_locks` + `successors`): `ts::task(fn).after(x, y).launch()` runs once every prerequisite has *settled*; a **cancelled prerequisite propagates** — it releases the dependent but marks `prereq_cancelled`, so the dependent settles cancelled instead of running (uniform with `then`, via the block's `prereq_cancelled` flag checked in `Executable::run`). `detail::submit_ready` bridges the counter to the scheduler. This is the same mechanism as the graph's indegree (the graph/`when_all` rebase onto it is pending). **Reusable tasks**: no new type — `Task_control_block::reset()` re-arms a settled block in place (monomorphic, scalars only), and the `Task_builder<R>` from `ts::task(fn)` is the reusable handle (it retains the block after `launch()`; also has `reset()`/`sync()`/`is_done()`): `t.reset().after(x).launch(); r = t.sync()` re-runs one block/body/result-storage (one run in flight; `reset()` guarded by the block's `ready` flag). `Signal::reset()` gives a reusable phase gate. **Nested tasks**: `ts::nested(fn)` / `ts::add_nested(task)` (via a `current_task` TLS) from inside a running body gate the parent's completion — the `num_locks` `execution_flag` bit flips it from counting prerequisites to counting nested tasks. **Retraction**: a blocking `sync()` on a *retractable* (bare `launch`/`task`, not pipe/`async`), ready, not-yet-started task runs it **inline** on the waiting thread (a `started`-claim keeps a worker and the retractor from both running it) — this breaks the oversubscription deadlock (nested fork-join blocking all workers). **Deep**: `sync()` on a dependent walks its `prerequisites` (backward links) and runs the whole un-started subtree inline, so waiting on a join (not just leaves) is deadlock-free too. **Inline dispatch**: `ts::task(fn).set_inline().after(...)` runs a ready task on the thread that settled its last prerequisite (not the queue) — the dispatch forks in `release` (`dispatch_ready`), bounded by a per-thread FIFO trampoline (`inline_pending` + head index) so deep inline chains don't recurse; caveats (nondeterministic/external thread, bypasses priority, must not block) are documented not enforced. Static dispatch bits (`priority`/`retractable`/`run_inline`) are packed into a `Flags` byte on the block. See `docs/task-internals.md` §2/§4/§6/§7. **`Signal`** is a bodyless `Task<void>` completed by hand via `trigger()` (idempotent) — an integrated done-signal / barrier / phase gate (UE's `FTaskEvent`). **Cancellation**: `Cancellation_source`/`token` (cooperative); `async`/`then`/`execute` take an optional token; not-yet-started work is skipped and cancellation propagates down continuations/successors as a completion state (`Task::is_cancelled()`); a cancelled value `sync()` is fatal (check first), a cancelled `void` sync() unblocks. **Body-level early-out (opt-in)**: any task body that declares a trailing `Cancellation_token` parameter (`[](Cancellation_token t){...}`, `[](T& v, Cancellation_token t)` for `async`, or a `then` continuation in any shape) receives the block's token (forwarded by `Executable::run`; `Task_result_t`/`Async_result_t`/`Invoke_result_tok` derive the result type off the token-arity overload) so it can poll `is_cancel_requested()` and early-out for cancellation arriving *mid-run* — a cooperative return settles the task **completed**, not cancelled. Covers `task`/`launch`/`nested`/`async`/`then`. A cancelled `when_all` prerequisite cancels the join (it can't form a tuple) rather than stalling. **Push notification**: `Cancel_callback(token, fn)` (RAII, `std::stop_callback`-style) — `request_cancel()` fires registered callbacks synchronously, for work that blocks rather than polls; source/token/callback share a `detail::Cancel_state` (atomic flag + mutex-guarded callback list).
- **`Static_task_graph`** (`static_task_graph.{h,cpp}`) — build-once / run-many DAG. `add_node(fn, Guarded<>&...)` deduces per-arg access from the functor's parameter const-ness (via `Function_traits`; non-generic lambdas / function pointers only) and returns a `Graph_node` — a build-time ordering handle (`after`/`before`), not a completion handle (run-many means a node has no single result). `compile()` derives edges from access conflicts (shared instance + at least one writer, ordered by declaration index) plus explicit `after`/`before`, dedups, Kahn cycle-checks. `execute()` runs the DAG in parallel via atomic indegree counts; re-runnable; returns a completion `Task<void>`. Each node runs as a real task block (a `Graph_node_block`, §7.1), so its body may spawn **nested tasks** (`ts::nested`) — its completion (and thus its successors + object release) gates on them — and nested sub-work inherits the node's `Access_context` by value (`ts::launch` snapshots it), so it may touch the node's owned guarded data. Node blocks + the `Run_state` are built at `compile()` and re-armed per run (nodes dispatch via the raw scheduler API; completion via the block's persistent `on_complete` fn-ptr, not a per-run continuation), so a run allocates only its `done` handle — re-runs are essentially allocation-free (~19% faster than per-run blocks). The graph is movable (`execute()` refreshes the blocks' back-pointers); runs are sequential (one at a time). Nodes access their objects **directly** (bypassing the pipe), so each node **acquires** the objects it touches (`pipe_acquire`/`pipe_release`, mode-aware) before running and releases them at completion — a concurrent `Guarded::async` on the same object queues behind the node that holds it instead of racing it (the harness does *not* catch that race — both sides declare access). Acquire is **per-node, mode-aware, canonical-order incremental** (ascending pipe-index; deadlock-free): an object is held only over each accessor's `[acquire, complete]` window — free in the gaps for async (a gap node between two accessors leaves it free), and a **reader** node holds it as a reader so a concurrent async read (or another reader node) overlaps; a **writer** node is exclusive. Replaces the old whole-run writer-only reservation. **Inline dispatch** (`Graph_node::set_inline()`): a ready node runs on the thread that settled its last prerequisite when it can acquire all its objects *synchronously* there (via the shared `dispatch_ready` trampoline); a contended object defers it to the queue — the "revoke predecessor's access, acquire successor's, else defer" hand-off. **Object handoff**: `node_complete` hands a held object *directly* to the sole ready successor that takes it in the same mode (skip release + re-acquire — the pipe state is already right; a `preheld` bitmask makes the successor's `acquire_next` skip it), instead of the release/re-acquire round-trip; unique for writers by the conflict edges. Non-handoff objects are released (the gap-freeing). See `docs/task-internals.md` §10 for the mechanism + the scenarios that still break (blocking on same-object async in a node, concurrent/nested runs on shared objects, incomplete declarations).
- **`Deferred<T>` / `Versioned<T>`** (`journal.h` + `deferred.h` + `versioned.h`, header-only; `journal.h` holds the shared staging machinery — `detail::Journal`, `Recorder`, `Parallel_recorder`) — the deferred-write layer from `docs/command-buffer-design.md` (design 4, implemented; vocabulary: **stage / commit / publish**). `Deferred<T>` binds to a `Guarded<T>`: `recorder()` mints move-only producer handles whose `stage(closure)` appends to private per-recorder storage (**no grant on the target**, contention-free between recorders — `detail::Journal<T>`, shared machinery); `commit_async(opts)` applies everything as ONE ordinary pipe write (cut at execution time, so a cancelled commit retains its commands), `commit(T&)` applies under a write grant the caller already holds (graph node / async body — checked via `access_check`). Apply order is deterministic: recorder-creation order, FIFO within — independent of thread timing. Producer→commit ordering is hand-wired (`after`); `Access::append` edge derivation is deliberately deferred. `Versioned<T>` = journal + two replicas behind one `Guarded` front (readers declare ordinary read on `state()`; the swap exchanges CONTENTS, so the front's address is stable — zero graph/pipe/harness changes): `read()` sees the last published version all frame (no read-your-writes — outputs arrive as the NEXT version), `publish()` is a **three-phase** step where only the swap holds the write grant — (1) cut + apply to shadow, grant-free; (2) swap, ~ns; (3) resync as a **pipe read job**, overlapping readers of the new version while FIFO holds the next writer (incl. a graph flip's acquire) behind it — the pipe is the shadow-ownership chain; consecutive publishes also chain phase 1 after the previous resync internally (an empty publish doubles as a resync fence). Graph form: `ts::publish_body(v)` as a node with write on `v.state()`. Resync policy per instance: `replay` (default — re-apply the batch; both applications see bit-identical pre-states, so deterministic commands give bit-identical replicas; **commands must be deterministic**), `copy` (user fn or copy-assign), `overwrite` (writer rewrites everything; no resync). `set_divergence_check(hash)` fatals on replica mismatch after replay (bitwise — replay has no FP drift on one binary). Staged-but-unapplied commands at destruction are **fatal** under `TS_SAFETY_CHECKS` (lost writes); `discard()` is the escape. Selection rule: `Versioned` is for state whose per-frame delta is *data*; when producing version N+1 is heavy computation (physics sim), keep ONE instance behind `Guarded` and version its output *extract* — see `sample/physics.cpp` (sealed `Guarded<Physics_world>` with exactly two grant holders, `Deferred` inputs, `Versioned` pose snapshot, id-reservation forward refs, batch-extract idiom; deterministic across runs). Known v1 costs: closure-tier commands (`move_only_function`, per-command alloc past SBO — typed-POD/arena tier pending, alloc-audit), per-slot mutex on stage (uncontended one-producer use; exists for the dynamic stage-vs-cut race). **Parallel staging**: `parallel_recorder()` mints a per-WORKER handle (slots keyed by the scheduler's `current_worker_index` TLS + an overflow lane for non-worker threads — the `parallel_for` caller's share, retraction/inline bodies) for ONE producer parallelized internally: contention-free under any chunking (guided/stealing/long tail), but cross-thread apply order is nondeterministic — use it for per-key-single or commutative commands (or a sorted commit); index-keyed `Recorder` lanes remain the raw-determinism answer. Batch order is still fixed at the cut, so `Versioned` replay stays exact either way. **Ordering contract** (journal.h): intra-recorder FIFO is semantic — build on it; **cross-recorder order is arbitrary — never build semantics on it** (same-key cross-producer writes are a conflict; fix = one writer per key / commutative commands / future sort keys), but it IS deterministic given a deterministic mint/destroy sequence, so runs are reproducible (bugs included). Recorder dtors release their slots to a free-list (live slots bounded by peak concurrent recorders — mint/destroy per frame no longer grows the journal; staged-but-uncut commands survive release); a reused slot keeps its position — observable only to programs already violating the contract. Keeping >4096 recorders alive is fatal under `TS_SAFETY_CHECKS` (`Journal::max_slots` — catches mint-and-retain-per-frame). Recorders must not outlive their `Deferred`/`Versioned` (dtor touches the journal). **Pattern recipe — blackboard**: no new type; shared board = `Versioned<Blackboard>`, private board = plain member, key-change notification = dispatch node after the flip + per-subscriber value diff (doc §7.4; single-file sample `sample/blackboard.cpp`).
- **Access harness** (`access.{h,cpp}`) — `TS_CHECK_ACCESS()` at the top of every guarded method checks `this` against a thread-local `Access_context` the scheduler/pipe installs per task; a violation routes to `ts::fatal`. ~1 ns/call. Subtasks (e.g. `parallel_for` chunks) inherit the parent node's context. Gated by `TS_SAFETY_CHECKS`.
- **`fatal.{h,cpp}`** — exceptions are disabled project-wide; all non-recoverable failures call `ts::fatal` (message + `std::stacktrace` + `abort`). Tests are the one place failures are non-fatal (the harness records and continues); fatal paths are checked via subprocess death tests.
- **Sample** (`sample/`) — a 17-system mock game-engine frame exercising all four layers; `run_frames` returns `Frame_stats` for the integration assertions. ~3x speedup over the serial budget at 60 fps. The AI system fires speculative `nav` queries via `Guarded::async` and cancels the batch after its own work — each query body opts into cooperative cancellation (trailing `Cancellation_token`, polled in its budget loop) and early-outs (`nav_early_outs()`), demoing the body-level early-out in the engine.
- **`task.h`** — holds the scheduler-independent core `Task<R>` layer moved out of `guarded.h`: `Cancellation_source`/`Cancellation_token`, the fully-monomorphic `detail::Task_control_block` + the `Result_block<R>` wrapper (result composed in, handle aliases the block's `core`), the apply-style `then` traits, `Task<R>`, `when_all` (+ its detail helpers), `Signal`, and the bare-scheduler task primitives `ts::task`/`ts::launch`/`ts::nested` (they dispatch through the `submit_ready` bridge, so no direct scheduler dependency; both the eager `launch` and the builder `task` inherit the launcher's access grant via `detail::with_inherited_access`). Header-only/templated — no `task.cpp` (the translation unit was removed). References nothing from the scheduler/pipe (`fatal.h` + `access.h` + std headers only — `access.h` for grant inheritance, which is scheduler-free); `guarded.h` includes it.

## Terminology

Use these terms precisely, in code and discussion:

- **spin waiting** — yielding in a loop until a condition holds (e.g. the worker idling on an empty queue, or a fixed-duration `spin()`). Does no other work.
- **busy waiting** — doing *unrelated* work while waiting, e.g. a thread that pops and executes other queued tasks while waiting for a specific task to complete. Usually a bad idea (stack growth, latency, priority inversion). Not the same as spin waiting.

## Design Principles & Lessons

- **Granularity decides parallelism.** Whole-object (system-level) access serializes every reader against any writer, collapsing the DAG toward sequential. Shard mutable state — the sample double-buffers transforms (`world_xf_prev` read by early systems, `world_xf` written by propagation and read by late systems, swapped per frame) so many readers don't contend with the writer. The central tension: static safety wants coarse access sets, performance wants fine ones.
- **Completeness hazard.** The graph's safety holds only if its access declarations are *complete*. A manual task or an escaped reference touching a system the graph believes it owns races — and the graph can *promote* a latent bug to a live one by manufacturing parallelism around it. The harness is the runtime oracle for undeclared access.
- **Never block inside a graph node / task.** Cross-system async access is fire-and-forget; consuming a result needs a continuation into a downstream node, not a `sync()` inside the node. Blocking ties up a worker and risks deadlock under worker exhaustion.
- **Sync state shared across threads must outlive every participant** — heap it (`shared_ptr`), never leave it on a stack frame the initiator may unwind first. (This cost a real use-after-free in `parallel_for`: the caller returned on `completed == chunks` and unwound while a helper still touched the stack counters.)
- Prefer per-instance runtime config over templating when a `thread_local` singleton would fracture across instantiations. Prefer a counting semaphore over a condition variable for worker wake (decouples from the queue mutex; survives a future lock-free queue). Prefer intrusive / zero-alloc on hot paths; avoid virtual dispatch.
- **Prefer intrusive ref-counting over `std::shared_ptr` for types we control.** Use the generic `detail::Ref_counted<T>` (CRTP base) + `detail::Ref_ptr<T>` handle + `detail::make_ref<T>()` in `ref_count.h`: one allocation (not two), a one-pointer handle (not two words), fewer atomics. Reserve `std::shared_ptr` for interop with external types. `Task_control_block`/`Task_ptr` keep their own hand-rolled variant (it aliases inside `Result_block`/`Executable` wrappers, so it needs a `destroy` thunk rather than `delete T*`). Converted so far: `Cancel_state`, `Multi_async_state`, and `when_all`'s `Join_state`.
- **Allocation discipline (hot paths).** Never spray separate heap allocations for individual small fields — `when_all` did this wrong (four `make_shared` for a slots tuple, an `atomic<int>`, an `atomic<bool>`, and a `std::function`, plus two blocks = ~6 allocs/join, the worst per-op offender). **One state struct, one allocation** (ideally the intrusive block itself); fold counters/flags/continuations in as members. A per-type recycling free-list is trivial because each `Exec<Body,R>`/`Result_block<R>` instantiation is a *constant* size (variable across types, const per type). Reserve bump/linear (arena) allocation for provably scope-bounded lifetimes (a `parallel_for`, a graph run, a frame with no escaping tasks). Prefer a tunable-SBO callable over `std::move_only_function`/`std::function` (size the inline buffer to the common task-functor size so the closure never heaps), and small-vector (inline capacity) or intrusive links for the block's `successors`/`prerequisites`/`continuations` (usually 0–1 elements). See `docs/TODO.md` 3.1 for the ranked plan.
- **Debugging flaky crashes**: localize with `main`'s `--tests` / `--bench` / `--stress`, categorize exit codes (1 = a `TS_CHECK` failure via `summary()`; `0xC0000005` = an access violation), and build `/p:EnableASAN=true` to get the faulting stack. Get the stack before theorizing — inspection alone misled twice.

## VS Project

`task_system.vcxproj` must be kept in sync manually — VS does not auto-discover files. Whenever you create a new `.cpp` or `.h` file, add it to the appropriate `<ItemGroup>` in `task_system.vcxproj`: `<ClCompile>` for `.cpp`, `<ClInclude>` for `.h` (use the path including subfolder, e.g. `tests\foo.cpp`).

Layout: core sources at the repo root, tests in `tests/`, benchmarks in `benchmarks/`. The x64 configs set `AdditionalIncludeDirectories` to the root + `tests` + `benchmarks`, so `#include "x.h"` resolves regardless of which folder the file lives in.

Tests use the harness in `tests/harness.h`: `TS_CHECK(cond)` (non-fatal, prints a stacktrace on failure), `run(name, fn)`, `summary()`. Each group lives in its own `tests/<group>_tests.{h,cpp}` with a `run_<group>_tests()` entry, wired into `run_all_tests()` in `tests/tests.cpp`. Fatal paths are exercised via subprocess death tests (`ts::test::expect_death("<scenario>")` + a case in `run_death_scenario`).

`main` takes isolation/stress args (no arg = run everything): `--tests` (suite only, returns the failure count as exit code), `--bench` (benchmarks only), `--stress` (sample only, many frames at a fast scale — dense workload for sanitizers), `--death <scenario>` (internal, the death-test child). These exist to localize flaky failures: run one component in a loop, categorizing exit codes (1 = a `TS_CHECK` failure via `summary()`; `0xC0000005` = an actual access violation), and build with `/p:EnableASAN=true` to get the faulting stack rather than guessing.

## Session Guidance

- Multiple sessions will work on different aspects — read this file for context each time
- Propose design options with tradeoffs before implementing non-trivial changes
- Perf matters: flag any change that adds allocations or contention on hot paths
- **Offload long or open-ended work to a background agent** so the main session stays interactive: bug investigations (deadlock/heisenbug hunts, TSan/ASan triage), long test/benchmark/loop runs, and multi-file research. Launch a `fork` (inherits context) or a fresh agent, keep chatting, and fold in its findings when it reports. Reserve the main session for design discussion and the actual edits.
- **Stream failures from long verification loops — don't wait for a final total.** A repeat loop should surface a hang/failure the instant it happens so investigation can start while the rest of the loop runs. Use the streaming pattern (emit one line per hang/failure; a final "done" line) rather than one summary at the end — e.g. a loop that runs each config under a per-run timeout and echoes only on `timeout`/non-zero-exit/`ASan`/`N failures`. Note: `Start-Process`'s `$p.ExitCode` reads `$null` on success in this setup (a known quirk) — check the real exit via direct invocation + the `"N failures"` line, not `Start-Process`'s exit code, or the loop will report false failures.
- After any change to concurrent code (scheduler, `Guarded` pipe, graph, `parallel_for`), verify with ThreadSanitizer: `bash tsan/run.sh` on a Linux host (TSan has no Windows runtime — see `tsan/README.md`). On Windows, ASan (`/p:EnableASAN=true`) + stress loops are the fallback (they catch memory bugs/UAF, not pure data races).
- Code style:
  - Type names are `Snake_case`: capitalized first letter, underscores between words — `Static_task_graph`, `Access_context`, `Guarded`, `Task`. This applies to all types including class templates (`Task<R>`, not `task<R>`).
  - `snake_case` for members/locals/functions; trailing `_` for private members.
  - Allman braces (opening `{` always on its own line, including namespaces, class/struct declarations, and lambdas):
    ```
    auto lambda = []()
    {
    };
    ```
    Short lambdas may stay one-liners (`[](int x){ return x + 1; }`); use Allman only when the body spans multiple lines.
  - Never align code or comments with padding spaces (no aligning `=`, parameters, trailing args/comments, or braces across lines). Single space only.
  - In comments, wrap references to code identifiers (type, function, variable, member names) in backticks: `Guarded`, `pipe_enqueue`, `current_access`.
