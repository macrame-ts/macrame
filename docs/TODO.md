## Task chaining / results
- **Rename `get()` → `sync()`: done.** `get` under-sold the cost (it *blocks*, and may retract + run a whole subtree inline); `sync()` signals a synchronization point. `Task<R>::sync` / `Task_builder<R>::sync` (`Signal` too, as a void `Task`). Considered `join`/`await`/`block_get`/`wait_get`; `sync` chosen. Smart-pointer `.sync()` (`Task_ptr`, `shared_ptr`) and `std::get<>` are untouched.
- Typed prerequisite -> subsequent chaining (dynamic path): **done** — `Task::then` (single) and `when_all` (multi, results as a tuple).
- Apply-style `when_all`: **done** — `then` unpacks a tuple result into separate continuation args (`then([](A& a, B& b){...})`) when the functor doesn't take the tuple by reference; falls back to the tuple form otherwise.
- `when_all` with void prerequisites and move-only results: **done** — void prerequisites act as pure ordering and drop out of the result (all-void → `Task<void>`); non-void results are carried in a tuple and **moved** (move-only supported). The consumer of a prerequisite's result is `when_all` (results move out), consistent with the single-consumer model.
- Typed chaining in `Static_task_graph` (graph nodes are void-only for now): let a node consume prerequisite-node results.
- **`sync()`/`then()` interaction — decided (2026-07): `const&` default + explicit `take()`.** Today a value `sync()` *moves* the result out (`std::move(*result_ptr)`), so a value task is single-consumer and `sync()` twice / `sync()`+`then` / two `then`s read moved-from storage. This copied `std::future::get()` reflexively. But `future` moves for three reasons — (1) move-only results, (2) zero-copy ownership handoff, (3) one-shot state release so the shared state can drop — and only (1)/(2) apply to us: reason (3), the lifetime constraint that forces std to split `future`/`shared_future`, does **not** apply because our handle *owns* the block (`core_` is a refcounted owner), so a `const R&` into the stored result stays valid as long as the caller holds the `Task<R>`. Plan:
  - `const R& sync()` — **non-consuming, the default**. Multi-consumer: any number of `const&` readers (`sync()` twice, `sync()`+`then`, N blocked waiters) — the result is immutable after settle (only `reset()` rewrites it, guarded), so concurrent reads are race-free. Removes the double-consume footgun entirely.
  - `R take()` (or rvalue-qualified `sync() &&`) — the **destructive move**, for ownership handoff and move-only `R`. `when_all`'s move-into-tuple becomes an internal `take`.
  - The contract shifts from "one consumer" to "**at most one mover, and it must be last**." Supersedes the earlier "fail-loud on double-consume" idea (no longer needed — `const&` doesn't consume). `void` sync() is unchanged (CV wakes all waiters; a `Signal` is a barrier).
- Cancellation: **done** — `Cancellation_source`/`token`; cooperative, checked when a task/node is about to run (not-yet-started work is skipped). Cancellation is a completion state that propagates down continuations and graph successors (`Task::is_cancelled()`); `async`/`then`/`execute` take an optional token; a cancelled `void` sync() unblocks, a cancelled value sync() is fatal (check `is_cancelled()`). A cancelled `when_all` prerequisite cancels the join (it can't form a tuple) instead of stalling — **done**. Cancel *callback* (push notification) — **done**: `Cancel_callback(token, fn)`, RAII/`std::stop_callback`-style; `request_cancel()` fires registered callbacks synchronously (for work that blocks rather than polls). **Body-level early-out** — **done**: a body that declares a trailing `Cancellation_token` parameter (`[](Cancellation_token t)`, or `[](T& v, Cancellation_token t)` for `async`) receives the token so it can poll and early-out for cancellation arriving mid-run; a cooperative return settles **completed** (`Executable::run` forwards `core.token`; `Task_result_t` / `Async_result_t` derive `R` off the token-arity overload, `Async_accessor` keeps the read/write disambiguation working with the extra param). Covers **every** task-body route: `task`/`launch`/`nested`, `async` accessors (read + write), and `then` continuations in all three shapes (void / whole-result / apply-style — `Apply_invocable_tok` / `Invoke_result_tok` extend the detection). A `then` body forwards the continuation's own token (`opts.token`), checked at dispatch too.
- **Task-builder / result-chaining direction** (research, 2026-07): surveyed UE, Taskflow, TBB, HPX, Folly, std::execution, Cilk, GCD, Java CF, .NET, Rust/tokio, Naughty Dog. Findings: a *single-task* configure-then-launch-later builder is the least-used pattern surveyed — where offered (.NET cold `Task`+`Start()`, Rust `task::Builder`) it's avoided; systems fix prereqs *at launch* (UE `Launch(prereqs...)`, tokio `spawn`, ND counters). The *graph* build-then-run(-many) flavor is common and load-bearing (Taskflow, TBB flow graph, senders) — our `Static_task_graph` is squarely in that camp. Result chaining (`.then` typed) is domain-split: essential in server/IO async (Folly/HPX/CF/senders) but with a callback-hell reputation the industry hides behind `async`/`await`; **largely avoided in game engines** (UE has no `.then`, ND uses counters + in-place mutation, blocking `GetResult()` as last resort). Implications: our `ts::task(fn).after(x).launch()` reads as "prereqs-at-launch spelled fluently" (fire-once setup sugar, not a long-lived reconfigurable object), which dodges the discouraged-cold-`Task` objection; **do not** promote it into a persistent reconfigurable builder. `then`/`when_all` typed chaining is a genuine UX nicety but expect real engine use to lean on prerequisite ordering + in-place mutation. Decision on **results-on-`after`**: leaning *no* — result-passing across a prerequisite is `when_all + then` by construction (the producer's result must exist before the dependent's body is fixed), so adding it to `after` re-implements `when_all`; keep the two axes separate (`after` = ordering/cancel propagation; `then`/`when_all` = result flow). Revisit only if a concrete use-case wants a single-result prerequisite feeding one dependent without the tuple.

## Control block / allocation
- **Allocation audit — profiled (2026-07, `--memprofile` / `TS_MEM_PROFILE`).** Deterministic allocs/op: `launch` **2**, `async` **3**, `then` **7.2**, `when_all` **12.7** (composite: 2 async + join + then), `parallel_for`/`graph` **1**; block = 288 B; malloc ≈ 30 ns uncontended. **Finding:** allocation is a *secondary* cost — dominant only on the leanest path (bare `launch` ~1/3 of the op); richer ops are dominated by µs-scale cross-thread scheduling latency (allocs 1–13%), and the pool A/B showed no dramatic, uniform win (Segment Heap handles contention). So: reduce allocs for throughput/cache + the lean per-frame task path, but don't expect a 2× — the scheduling path is the primary lever. Ranked plan:
  1. **Kill the per-dispatch `submit_closure` `new move_only_function`** — IN PROGRESS. The surprise from the profile (`launch` = 2, not 1): every queued task heaps a closure box to bridge to the raw `void(*)(void*)` scheduler API. Pass block+gen via a widened `Task_entry`/block field instead. Highest-frequency win (hits *every* queued task).
  2. **Per-type recycling free-list** for `Exec<Body,R>`/`Result_block<R>`/bare block — each instantiation is const-size, so a `thread_local` free-list recycles with zero fragmentation. Helps the launch path + throughput/cache. **POSTPONED.**
  3. **`when_all` collapse** — DONE (6→2 via the intrusive `Join_state`, commit 4087626).
  4. **Tunable-SBO `Function<Sig, N>`** replacing `std::move_only_function`/`std::function` (user sizes the inline buffer to their common task-functor size → common closure never heaps); covers the block's `continuations`, pipe `Job`, and any remaining closure. **POSTPONED.**
  5. **Small-vector / intrusive links** for the block's `successors`/`prerequisites`/`continuations` (usually 0–1 elements → the heap alloc is pure waste; also shrinks the block by ~72 B). **POSTPONED.**
  6. **multi-object `async` `std::map` → sorted `vector`** (kills per-object red-black node allocs). **POSTPONED.**
  7. **Opt-in scoped bump arena** (ConcurrentLinearAllocator-style) for provably scope-bounded work — `parallel_for`/graph-run automatically, per-frame by user opt-in (caller asserts no task escapes the frame → bulk-reset at frame end). The ceiling for the per-frame engine audience. **POSTPONED.**
  Note the block's mutex+CV are ~152 B of the 288 B — a lighter wait primitive (futex) roughly halves the block, doubling pool density (ties to the platform layer).
- **Keep `Task_control_block` as small as possible; fuse flags into bits.** Started: `Flags` packs `priority` (2b) + `retractable` (1b) + `run_inline` (1b) into one byte (`priority`/`run_inline` read together at dispatch). Still to audit: `completed`/`cancelled` (bools under the mutex — could be bits), the fn-ptrs (`execute`/`on_complete`), and whether the several vectors can be intrusively linked. A smaller block matters — every task allocates one, on hot paths.
- **Reconsider every `shared_ptr`; prefer intrusive ref-counting.** The block, its `successors`/`prerequisites`/`continuations` vectors, and the public handles are all `std::shared_ptr<Task_control_block>` — each a separate heap control block and an extra atomic per copy. Move to an **intrusive** refcount (a count word in the block itself + a small `Task_ptr` handle): one allocation instead of two, smaller/faster handles, fewer atomics, and the aliasing tricks (`Result_block`/`Executable` wrappers) get simpler. Cross-cutting — do it deliberately, with TSan/ASan coverage.

## Guarded / access
- **Standalone public `Pipe`?** Expose the reader/writer pipe as a public serialization primitive (UE's `FPipe`): serialize a stream of tasks without wrapping a single `T`. Open question — does it earn its keep over `Guarded<T>`, which *is* a pipe + an owned `T` + access deduction + harness, just friendlier? It only adds value when the serialized resource isn't one wrapped object: several objects that must move in lockstep, external/global state, or pure task-stream ordering. Defer until such a use case shows up; if your resource is one object, `Guarded<T>` already covers it.
- **Adopted `Guarded`** (undecided) — `Guarded<T>` wrapping an **existing** instance (borrow/adopt) instead of always constructing `T` in place. Design ownership/lifetime (borrowed vs owned): owned stays a by-value member (no indirection); borrowed = a `T*` + `owned_` flag via an `adopt` ctor tag; the destructor still drains the pipe (`wait_until_idle`) but does **not** destroy a borrowed `T`; access key = the borrowed address so `TS_CHECK_ACCESS()` inside `T`'s methods matches what the pipe declares. Widens the completeness hazard (the borrowed `T` is reachable via its original path too — all access must still route through the wrapper; harness is the oracle). UE's `FPipe`-separate-from-resource model.
- **Pipe FIFO semantics + reader/writer policy — researched (2026-07): keep `fifo`, relaxations are staleness opt-ins, fix inversion via inheritance.** FIFO-with-reader-coalescing is not a stylistic choice — it *is* the serialization contract (writes totally ordered; each read observes exactly the writes submitted before it). Reordering a writer past an earlier reader, or a reader past an earlier writer, **changes observed values** — a wrong answer, not a scheduling nuance. So in a submission-ordered pipe the `writer_priority`/`reader_priority`/`batch_readers` knobs are **not** free throughput levers (my first framing was wrong — that conflates a *lock* — Go `RWMutex` writer-preference biases an acquire race with no predefined order — with a *queue*, which has a fixed order). Conclusions:
  - **`fifo` + reader coalescing is the sole value-preserving policy** — keep it as the only default. Strict-serial (UE `FPipe`) is just this minus reader concurrency (strictly worse). The only safe reader-parallelism is coalescing the *consecutive* readers, which we already do.
  - **Relaxations are explicit staleness opt-ins**, not scheduler choices: a reorder is legitimate only when the reads are declared "latest-value / staleness-OK" (position-independent) — a property the user asserts about the reads. Expose (if ever) as a per-read / per-instance opt-in, loudly documented as changing what reads observe. Not a throughput knob.
  - **The genuine reader/writer throughput win is structural — snapshot / double-buffering** (MVCC-style: readers on a stable snapshot, writes applied at a sync point), i.e. the deferred/command-buffer item + what the sample already does by hand (`world_xf_prev`/`world_xf`). Put the ambition there, not into fancier pipe scheduling.
  - **Pipe priority inversion** (a `high`-priority `async` stuck FIFO behind low-priority pipe work) is real and orthogonal to the policy — fix it with **priority inheritance**, not reordering (see 7.5, of which the pipe is the linear special case): dispatch the pipe head at `max(own, max priority of all jobs queued behind it)` — same order, same observed values, but blockers clear at the urgency of their most-urgent waiter. O(1) with a per-level pending count (3 levels). Residual: a job already handed to the scheduler's MPMC queue can't be retroactively re-prioritized (no re-prioritize op); inheritance covers the still-in-pipe tail, which is where backlog accumulates.
- **Dynamic multi-object `async(fn, objs...)`: done** — free function `ts::async(fn, objs...)` (options first: `ts::async({.priority=...}, fn, objs...)`). Per-arg access from the functor's parameter const-ness (`Function_traits`, non-generic lambdas / function pointers). Acquires each object's pipe **mode-aware, in canonical (pipe-address) order, holding** (`multi_acquire` — the same `pipe_acquire`/`pipe_release` primitive as the graph, which shares the address order via its address-sorted `distinct_pipes_`, so nodes and multi-object asyncs can't deadlock against each other), runs `fn(*objs...)` under an `Access_context` declaring all, then releases via a completion continuation (`attach`). Deadlock-free by ordered acquisition (canonical order **with** hold — the standard result; "never incremental" was imprecise). Dedups a repeated object (write-wins). `run_inline` on the options is ignored (multi-object inline is a follow-up); token forwarding to a token-taking body is not supported (arity must match object count). Tests: basic, exclusion vs single-object async, no-deadlock (opposite declared orders), options.
- Deferred / command-buffer write option (read snapshot, apply writes at a sync point) as an alternative to in-place serialized writes.
- **Generic double-buffering / versioned snapshots (potentially RCU-based).** The real reader/writer *throughput* answer for our audience (coarse, big, read-heavy guarded objects — see 4.4): rather than serialize every reader against the writer on the pipe, let readers run lock-free on a stable published version while a writer prepares the next, swapping at a sync point (what the sample does by hand with `world_xf_prev`/`world_xf`). Generalize into a reusable primitive. Study **`folly::rcu`** as the reference (readers hold a version, writer publishes a new one, old versions reclaimed when no reader holds them). This is the structural win — copying the whole `T` (folly `.copy()`) does NOT fit our big-object audience (task overhead + expensive copy); `Guarded` also should NOT require `T` copyable. Interacts with the deferred-write item above and the "granularity decides parallelism" lesson. Eval RCU vs a simpler double-buffer before adopting.
- **Access check for nested `Guarded` (subobject)** (undecided) — the harness guards at whole-wrapped-object granularity (`access_check(this)`, address-equality `grants()`), so a sub-object reference handed out by a wrapped system (`Body& b = S.get_body(i)`) isn't covered: `b`'s methods either aren't guarded (silent) or check `&b` against a context that only granted `&S` (false violation). Collides with the "granularity decides parallelism" lesson (you want fine slices, the oracle only knows top-level objects). Options, cheapest first: (1) **range containment** — a grant on `S` covers `[&S, &S+sizeof(S))`, `grants()` becomes a range check (~free, covers embedded sub-objects, misses heap members via pointer); (2) **explicit region handles** — a declarable sub-pipe/`Region<T>` carved from a `Guarded` so disjoint slices are independently granted (mind `Access_context::max_entries == 8`); (3) **hierarchical grants** — sub-object records parent, `access_check` walks up (most general, most cost). Lean: (1) for embedded, (2) when disjoint-slice parallelism over a container needs verifying.
- clang-tidy check enforcing that every public method of a wrapped type calls `TS_CHECK_ACCESS()`.
- Generic-lambda / `auto&` support for access-mode deduction (graph `add_node` currently needs non-generic lambdas so parameter const-ness is introspectable).

## Static_task_graph
- **Per-node mode-aware object acquire (M1.1a): done** — replaced the whole-run writer-only reservation with per-node acquire/release. Each node acquires the objects it touches (in ascending pipe-index / canonical order, holding each — `pipe_acquire`, mode-aware: a reader joins concurrent readers, a writer is exclusive), runs, then releases them at completion (`pipe_release`, mode-aware). So an object is held only over each accessor's `[acquire, complete]` window — **free in the gaps** (a gap node between two accessors leaves it grabbable by async; a late-touched object is free until its node runs), and a read node overlaps a concurrent async read (the old reservation blocked even reads for the whole run). Deadlock-free via canonical order (belt-and-suspenders — edges already serialise conflicting nodes, single-object async can't cycle); canonical order becomes load-bearing when multi-object `async` lands (M1.1 "for async"). Dropped `remaining_objects`/`remaining_accessors`/`object_initiated`/`pipe_accessors_`; `acquire_next` walks the objects. Tests: gap frees object between accessors, reader node overlaps async read.
- **Graph-node inline dispatch (M1.1b): done** — `Graph_node::set_inline()`. When a node's last prerequisite completes on a thread, `acquire_next` acquires the successor's objects on that thread; a `synchronous` flag tracks whether the whole chain stayed there (flipped false on the first `pipe_acquire` deferral). An inline node that stayed synchronous dispatches via the shared `dispatch_ready` trampoline (its block's `run_inline` bit set → inline path, bounded/iterative); otherwise it queues (`run_node`). So an inline node runs on the settling thread only if it acquires all its objects there-and-then; a contended object defers it to the queue — the "revoke predecessor's access, acquire successor's, else defer" hand-off. A chain of inline nodes on one object trampolines (each releases at completion, the next acquires synchronously). Caveats mirror `Task_builder::set_inline`; an all-inline graph runs synchronously on the `execute()` caller. Tests: inline root on caller, inline chain on caller, inline rerun; TSan `graph inline stress` (inline chain contended by async → defer path).
- Nested tasks inside a graph node: **done** — a node runs as a real `Executable` block (`current_task` set, `execution_flag` self-lock), so its body may `ts::nested(...)`; its completion (and thus successors + object release) gates on all nested tasks (§7.1/§8), and nested sub-work inherits the node's `Access_context` by value so it may touch the node's owned guarded data. Enables dynamic, runtime-sized fan-out over a node's store (what a static `parallel_for` can't express). Node blocks + `Run_state` are built at `compile()` and re-armed per run (dispatch via the raw scheduler API; completion via the block's persistent `on_complete` fn-ptr), so a run allocates only its `done` handle — ~19% faster than per-run blocks. Still one run at a time.
- **Object handoff between consecutive same-object accessors: done** — a node no longer releases + re-acquires an object across an edge to the next accessor. In `node_complete`, after collecting the successors this node's completion makes ready, each held object is **handed off** (skip release + skip the successor's re-acquire) when exactly one ready successor takes it in the **same mode** — the pipe state (writer_active / reader count) is then already correct, so the round-trip is pure waste. Unique for a writer (two writers of one object conflict → edge → not both ready). The successor's `acquire_next` skips a handed object via a per-node `preheld` bitmask (position in `pipe_indices`; set before the successor is triggered, so single-writer + happens-before). Otherwise the object is **released** (the M1.1a gap-freeing). The handed object stays held across the edge (no gap), which is fine — the successor just went ready and runs immediately (the eliminated gap is a dispatch-latency micro-window; for a queued successor it's bounded by its queue wait). Works for inline chains (each releases at completion → the next would re-acquire on the same thread — now handed directly) and queued chains alike. Tests: handoff write chain, handoff skips mode change; TSan graph+async stress uses a write→write→write handoff chain contended by async.
- `compile()`: ambiguity detection (two nodes with conflicting access and no explicit order edge) — currently auto-ordered by declaration index.
- Pipelined / concurrent execution (more than one execute() in flight) for frame overlap.
- Profiler-guided graph optimization (reorder/rebucket from measured task durations).

## Fork-join / parallel_for
- **Priority propagation / inheritance (7.5)** — **SHELVED (2026-07)** — designed, not scheduled; revisit when a workload shows priority inversion. One mechanism, three instantiations. **Principle:** priority flows *backward* along dependency edges (consumer → producer), taking max: `effective_priority(x) = max(x.own, max effective_priority of everything that (transitively) depends on x)`. A high-priority dependent drags its upstream critical path up to its own priority, because that upstream is exactly what makes it wait. This is the backward dual of cancellation (which propagates *forward*, prereq → dependent). Do **not** implement it by reordering — reordering breaks value semantics (pipe) or the DAG order; inheritance keeps order, only raises dispatch priority.
  - **(a) Pipe inheritance** — the linear special case (see the pipe item above): dispatch the pipe head at `max(own, max priority of jobs queued behind it)`. O(1) via a per-level pending count. Residual window: a job already in the scheduler's MPMC queue can't be re-prioritized.
  - **(b) Static graph — the cleanest, do first.** Because the graph is build-once/run-many, compute effective priorities **once at `compile()`**: a reverse-topological max-relaxation over the compiled edges (reuse the Kahn order from cycle-checking), `effective = max(own, max of immediate successors' effective)`, stored per node alongside `own`; each run dispatches nodes at `effective`. O(V+E), once. **No residual window** — priorities are fixed before any node dispatches, unlike the pipe/dynamic cases. Small implementation: the graph already stores per-node priority + the edge structure.
  - **(c) Dynamic chains** (`after`/`then`/`when_all`) — same rule, harder: the DAG is discovered incrementally, so donate at launch (when `H.after(P)` and `P` still pending, raise `P` and propagate up its unfinished ancestors), bounded by upstream depth, with the same residual window as the pipe. Do after (b).
  - **Caveat — make it opt-in / bounded.** Unbounded backward propagation can *defeat* prioritization: one high-pri consumer promotes a large upstream subtree to high; if common, everything floods the high queue and genuine low-priority/background work starves via promotion. Latency (finish H fast) vs fairness/throughput (don't drag background up) is the user's per-workload call — expose a per-graph / per-task flag or a propagation-depth cap (UE propagates deliberately, not always).
  - **Opt-in surface** (differs by case because flooding risk does; matches the house option-aggregate / fluent-builder style):
    - **pipe: on by default** (never reorders, bounded by pipe depth, pure latency fix) — per-instance escape only: `Guarded<Log> log{ {}, {.priority_inheritance = false} }`.
    - **static graph: off by default**, one compile flag: `g.compile({ .priority_inheritance = true })` (runs the reverse-topo pass). Per-node barrier to shield background nodes: `node.priority(Priority::low).no_inherit()`.
    - **dynamic chain: off by default, opt-in on the *consumer*** (it knows it's urgent; the producer doesn't know its consumers — and consumer-side opt-in is the flooding guard): `ts::task(render).priority(high).propagate_priority().after(cull, skin).launch()`; on the aggregates `producer.then(consume, { .priority = high, .propagate_priority = true })`. Producer shields itself with the same `no_inherit()`.
    - **blast-radius cap** (dynamic only; static is bounded by V, pipe is linear): `Scheduler{ { .max_priority_propagation_depth = 4 } }` (0 = unbounded default).
  - **Not OS thread priority.** Keep this in userspace (queue order + inheritance). Do **not** remap worker OS thread priority per task: it's a syscall (~µs vs ~200 ns dispatch), permission-gated on Linux (`CAP_SYS_NICE`, can't freely restore), and the wrong tool (arbitrates against unrelated threads/processes). Only GCD/macOS makes per-work-item QoS cheap+idiomatic (QoS adoption + inheritance + P/E-core steering — kernel-built for it). Legit OS-priority use is a **fixed per-pool** low-priority/QoS-background attribute set once at thread creation (UE fg/bg pools), so background task-system work yields to the machine — belongs in 7.4 (platform), maps to a macOS QoS class.
- **Reserve workers** (low priority) — oversubscription/standby fork-join. `ts::parallel_for` (core) and `sample/parallel.h` are already deadlock-free via **caller-participation** (the caller drains the loop + waits on work-done, so no worker parks idle while its own work is pending). The alternative: let a fork-join just **block** (`sync()`) and have the scheduler **wake a standby ("reserved") worker** to cover the now-idle core (UE 5.5 `IncrementOversubscription`, GCD's lazy pool). More general (rescues *any* blocking wait, not just `parallel_for`) and yields a simpler primitive, but: (1) **thread-explosion** risk — GCD's failure mode; nested fork-join cascades → needs a cap + accounting; (2) needs the **platform layer** — standby workers waking on a timeout require `park(addr, expected, timeout)`, and `std::atomic::wait` has no timeout (7.4/raw futex trigger); (3) subtasks must inherit the parent's `Access_context` (sample already does). **Sequenced after 7.4** (platform abstraction); low priority since caller-participation already covers the need.

## Scheduler
- **Task priorities: exposed** — the scheduler always ordered by `Priority {high, normal, low}`; now every queued route threads it to `scheduler.submit`: `ts::launch(fn, token, priority)`, `ts::task(fn).priority(p)`, `Guarded::async(fn, token, priority)`, `Graph_node::priority(p)`. Stored on the block (applied at dispatch, incl. prerequisite-gated). `then` now carries priority (and inline) via its `Continuation_options` (`t.then(fn, {.priority = high})`); `when_all`'s join is still bodyless (no priority — its consuming `.then` carries one). **Future — priority propagation / inheritance:** see the dedicated item below.
- **Inline execution mode: done (after/builder path)** — `ts::task(fn).set_inline().after(...).launch()` runs the task on the *settling thread*, not the queue. Dispatch forks in `release` at `num_locks == 0` (`dispatch_ready`): inline → run on this thread, else `submit_ready`. Bounded by a **trampoline** — `Task_control_block::inline_pending` (a thread-local retained-capacity vector) + a head index, drained **FIFO** (advance the index, `clear()` at end; no per-item pop, no steady-state alloc) — so a deep inline chain runs iteratively (O(1) stack; tested to 20k). `run_inline` is a packed bit in `Flags` (with `priority`/`retractable`). Remaining notes:
  - **External-thread execution.** An inline task may run on a thread with no worker context — a `Signal::trigger()` from a UI thread, a retractor. Whatever ambient context our workers rely on (current or future), an externally-run task must either cope with its absence or **detect and fail clearly**. (Not enforced yet.)
  - **Diagnostic — long-running inline tasks** (monopolize the completer, invert priority) and **a `sync()` that parks a worker** (generic): detect + warn — future profiling/diagnostics.
  - Scope: `after`/builder path, `then` (via `Continuation_options{.run_inline}`), `async` (via `Async_options{.run_inline}` — `pipe_try_inline`), **and graph nodes** (`Graph_node::set_inline()` — inline on the settling thread when it can acquire its objects synchronously there, else defer; see M1.1b). All four dispatch routes now support inline.
- **Unify continuations, then routes** (roadmap order): (1) inline on the `after` path — **done**. (2) rebase `then` (and `when_all` consumption) onto proper prerequisite tasks — **done**: a `then` continuation is now a real `Executable` with the producer as a `num_locks` prerequisite (queued by default → it gets a priority and the scheduler can slot work between; inline opt-in), its body reading `producer->result_ptr`; a *cancelled* producer still dispatches it (ordering-only), so `Executable::cancel_if` makes it cancel instead of consuming a missing result; deep-retractable via the prerequisite backlink. Retires the inline `then`-callback. (`when_all`'s *join* stays a bodyless aggregator + retraction hint; its *consumption*, the `.then` off it, is the rebased path.) (4) **async inline — done**: `async(fn, {.run_inline = true})` runs the body inline on the calling thread when the pipe is immediately free (`pipe_try_inline`, mode-aware: reader joins as a reader, writer exclusive; never jumps queued work), else enqueues as usual — the opt-in surface is the new `Async_options` aggregate replacing the positional `token`/`priority` params. (3) **static graph node inline — done** (M1.1b): `Graph_node::set_inline()` runs a ready node on the settling thread via the `dispatch_ready` trampoline when it can acquire all its objects synchronously, else defers to the queue; built on M1.1a's per-node acquire. **All four routes (after, then, async, graph) now inline.** See the "task = prerequisites + dispatch-route (scheduler/pipe/inline) + priority" model.
- ~~Spin-then-block hybrid idle (UE-style: spin N cycles, then park on an EventCount) instead of the binary spin/block policy.~~ **Done (2026-07).** `Idle_policy` modes: `spin_then_block` (UE-style, spin `spin_cycles` scans then park, producer wakes per submit — **now the default**) and `handoff` (Go-style — one spinner; a spinner that finds work promotes a successor before running; producer issues the wake syscall only on the fully-parked 0→1 transition, else a cheap epoch-`advance`, gated on `num_spinning_`; the always-advanced epoch keeps correctness independent of the advisory `num_spinning_` count, so no seq_cst fences → TSan-verifiable). Runtime enum (no measurable hot-path cost — one predicted branch + one relaxed load). Config: `Scheduler_config::spin_cycles` (default 64). Benchmarks: wake latency ~40% lower for both spinning modes (792→469 ns); throughput cost on uncontended streams. TSan-clean (`stress_idle_policy`). See `signal_submit`/`handoff_wait` in `scheduler.cpp`, `Event_count::advance`/`wake_one`. The bare park-immediately `block` mode was **removed** (2026-07) — it's just `spin_then_block` with `spin_cycles == 0`, and nothing needed a zero-spin default. Not built: the pure "producer never touches wake state" variant (needs seq_cst Dekker fences TSan can't model) — rejected for verifiability.
- **Per-worker work-stealing deques + lock-free global overflow queue** to replace the single mutex-guarded priority queue (the known scaling bottleneck). **Measured (2026-07, spin idle, submit-only contention sweep):** near-linear to 4 producers (p1 1.86 → p2 3.43 → p4 6.60 M/s) then a hard **plateau at ~6.4 M/s** (p6 6.36, p8 6.17, p12 6.39) — the single queue mutex serializes all submitters, per-op latency floors ~150 ns; adding cores past 4 buys nothing. This is M2. **Research done (2026-07, see the report):** surveyed oneTBB, TooManyCooks (TMC), Chase-Lev, Tokio, Go, Rayon, Cilk, Molecular Matters, Naughty Dog, Vyukov eventcount, and UE `LowLevelTasks` (`LocalQueue.h`/`WaitingQueue.h`/`Scheduler.h`, read on disk). Findings + design:
  - **Verdict on "central high queue + steal the rest":** adopt the *idea* (priority checked first, stealing for the rest) but generalize to the UE/TMC shape — **per-priority queues scanned high→low at every tier** — rather than a one-off central-high special case. No production WS scheduler uses a mutex+`priority_queue`. Make the global queues **lock-free MPMC**; add a **low-starvation valve** (serve low only after N high/normal, à la Go/Tokio's "check global every ~31/61") and a **Go-style spinner cap** (≤ ½ workers searching).
  - **Deque:** Chase-Lev, **bounded + overflow-to-global** (UE/Tokio/Go all bound — avoids the growable-array/ABA reclamation headache), owner LIFO push/take at bottom (cache-hot), thieves FIFO steal at top; Lê-Pop-Cohen-Nardelli C11 memory orderings verbatim (two `seq_cst` fences: one in take, one in steal; push uses a release fence). Worker `submit(normal)` → local deque; non-worker/external `submit` → global (no local deque); high/low → global (promote to per-worker deques later if profiling wants locality). Consider a Tokio/Go **single LIFO/`runnext` slot** for chained wakeups (throttle it — disable-after-3, un-stealable).
  - **Wake:** replace the counting semaphore with a **Vyukov eventcount** over per-worker wait nodes (`prepare_wait`/`commit_wait`/`cancel_wait` + epoch, Dekker seq_cst fence closes the lost-wakeup window; bounded `notify_n` avoids thundering herd). Preserves the block/spin `Idle_policy` (spin = never commit the wait). This is required anyway once tasks sit in local deques (the semaphore can't express "wake this parked worker").
  - **Staged rollout (TSan-gated at the deque step):** (1) replace the single mutex+`priority_queue` with 3 lock-free MPMC queues scanned high→low (keep the semaphore) — removes the comparator-under-one-mutex bottleneck, small verifiable win; (2) eventcount replaces the semaphore; (3) per-worker Chase-Lev deque for normal + steal phase (**the concurrency-critical step — mandatory TSan**); (4) starvation valve **(done)** + spinner cap **(done — the `handoff` policy's `num_spinning_`-gated wake is the cap: exactly one spinner drives discovery, successors promoted on handoff)**; (5) optional per-worker high/low deques.
  - **Platform abstraction (~6 functions):** `park(addr, expected, timeout?)`/`unpark_one`/`unpark_all` (Windows `WaitOnAddress`, Linux `futex`, macOS `__ulock_wait`/`os_sync`; `std::atomic::wait` to start but it lacks **timeout** — needed for standby/oversubscription workers + watchdogs — so plan the swap to raw futex), `thread_spawn`/`set_name`/`set_affinity`, `cpu_count`+minimal `topology`, `cpu_relax`/`yield`. Keep everything else (eventcount, deques, MPMC queues, scheduler loop) portable. Console = fiber backend behind the same `Task` API + core reservation via affinity; mobile = QoS classes + oversubscription/standby over a fixed large pool.
  - **Lower-level thread pool:** keep `std::jthread` for spawn/join, but **replace the semaphore with the eventcount + park/unpark abstraction** (UE's model — per-worker targeted wake + timeouts). Full custom thread creation only later for console fiber backends.
  - **Progress:** stage 1 (per-priority lock-free MPMC queues, `mpmc_queue.h`) — **done**. Stage 2 (Vyukov eventcount, `event_count.h`; replaces the semaphore) — **done**. Stage 3 (per-worker Chase-Lev deques for `normal` + stealing, `work_stealing_deque.h`; worker→worker submits go local) — **done**; measured +17% (block) / +22% (spin) on the new `fork-join` benchmark vs stage 2. Stage 4 (low-starvation valve) — **done**; **spinner cap — done** via the `handoff` `Idle_policy` (2026-07): its `num_spinning_`-gated wake caps discovery to one spinner + promotes a successor on handoff. (The plain `block`/`spin_then_block` searchers are bounded by `notify_one`; `spin` mode's steal-scan core-burn is opt-in by design.) Stage 5 (promote high/low to per-worker deques) — not started, profiling-gated. **Still needed:** a proper worker-submit benchmark with less shared-atomic contention to see the full deque scaling; the platform abstraction + eventcount timeout (still on `std::atomic::wait`).
- **Ambient (overridable) scheduler instead of a hard global.** `ts::launch`/`task`/`async` are hardwired to `default_scheduler()` (a process-wide static); only `Static_task_graph::execute(scheduler=…)` takes an explicit one. The global default is the RIGHT terse default for our audience (one frame-wide pool — UE/Go/Cilk agree; full explicit-per-launch à la senders/folly/asio would be call-site noise and fights our not-templated-on-executor block). BUT the *hard* global leaves testability (run on a deterministic/inline scheduler), embedding (a library on us imposes our pool on its host), multiple pools (fg/bg, per-subsystem), and named-thread targeting on the table. Fix = finish the ambient-context model we half-built (`thread_local current_scheduler` already exists): `ts::launch(fn)` stays terse, resolving to the *ambient* scheduler (current worker's, else a process default — tokio `Handle::current()`); add a **scoped override** `Scheduler_scope guard(s)` (tokio `enter()`) that sets the thread-local current for a region (zero call-site churn for tests/embeddings/subsystems); optionally a per-op override `Launch_options{.scheduler=&s}` for one-offs; `Guarded` binds the ambient scheduler at construction/async-time. Retires four limitations at once and **unifies with named-threads** (a named thread = a single-worker scheduler you target). Not full-explicit, not hard-global — overridable ambient.
- **Run-on-all-workers**: submit a functor to run once on *every* worker thread (broadcast). Uses: per-thread init/teardown, flushing thread-local state, per-worker warm-up. Needs a way to fan out to N workers and join.
- **Named-thread affinity** (avoid where possible, but unavoidable for legacy / thread-affine resources: render/RHI thread owning the GPU context, main/UI thread, audio thread). A **named thread can be modeled as a separate single-worker `Scheduler`** — then targeting it is just "launch/resume on that scheduler" (`co_await resume_on(render)` bounces a coroutine there and back), which unifies with making the scheduler an overridable context (see the global-vs-explicit-scheduler question). Prefer designing work to not need it; provide the escape hatch.
- **Timed / delayed tasks**: "run this in 300ms" — a delay queue (min-heap by fire-time or a timing wheel) that launches a task when due; one-shot vs periodic; cancellable pending timer; interacts with `Reusable_task` (re-arm on a timer).

## Coroutines / structured async
- **Coroutine support (`co_await`) — researched (2026-07), SHELVED.** Additive over the existing core, not a rewrite: make `Task<R>` **awaitable** (`await_ready`/`await_suspend`/`await_resume` — `await_suspend` registers the coroutine handle as a continuation on the block, i.e. `co_await` *is* `.then()` written linearly; `await_resume` returns `const R&` or moves via `take`, 1.6) + a `promise_type` aliasing a `Task_control_block`. Why it fits this project unusually well, and the design decisions:
  - **`Guarded` as an awaitable async-lock — the killer fit.** The pipe is already a FIFO reader/writer async lock; coroutines turn callback-`async(fn, obj)` into linear RAII: `auto g = co_await w.write(); g->step();` (mode explicit in the method vs deduced from lambda const-ness; multi-object = `auto [a,b] = co_await ts::acquire(x, y)` over the existing canonical-order multi-acquire). Exactly `folly::coro::Mutex::co_scoped_lock`.
  - **Access-context threading — the defining constraint — DONE (2026-07, in the spike).** The harness uses `thread_local current_access`, but a coroutine migrates threads across suspension. Model: **a coroutine is a chain of task-segments (code between suspension points); each segment runs under the coroutine's `Access_context`, re-installed on resume** — reuses the nested-task inheritance machinery (`snapshot_access` + `Inherited_access_scope`), no new concept. Implemented: `Task_promise` snapshots the ambient grant at creation (member init, on the creating thread, before the body); `Task_awaiter::resume_with_access` re-installs it via `Inherited_access_scope` around the async resume (a `requires` gate keeps `co_await` usable inside any coroutine; the sync-fire path needs no re-install — it continues the current segment on the current thread). Test `co access context` (resume outside the original scope proves the re-install). TSan/ASan clean. Remaining coroutine follow-ups: the `co_await w.write()` pipe guard (+ harness-as-suspension-detector) and scheduling the resume as a task-segment (currently inline on the settling thread).
  - **Lock-across-suspension peril → harness detects it for free.** `co_await`ing other work while holding a pipe guard serializes/deadlocks the pipe (the canonical coroutine anti-pattern). Rule: never `co_await` under a `Guarded` guard — and `await_suspend` can assert "no pipe grant in `current_access`" → `ts::fatal`. The project's signature safety mechanism catches the signature coroutine footgun.
  - **Exceptions OFF (`_HAS_EXCEPTIONS=0`) reshapes cancel.** No `throw` on cancel, `unhandled_exception()`→`ts::fatal`. Cancellation is **value-based** (a cancelled `co_await` settles the coroutine cancelled; or poll a trailing `Cancellation_token` between awaits) — aligns with the existing cooperative model, arguably cleaner than exception-based cancel, and forced anyway.
  - **Priorities/scheduling:** promise carries priority (TMC-style affinity); resumed segment dispatches at it; feeds 7.5 inheritance. Resume via **symmetric transfer** → maps onto the existing inline-dispatch trampoline (`inline_pending`), so deep `co_await` chains run iteratively.
  - **Structured concurrency:** `co_await ts::when_all(a, b)` is the linear join; spawn-N-then-await-all (TMC `spawn_tuple`/`fork`) over the existing `when_all`.
  - **Allocation caveat (ties to 3.1):** coroutine frames heap-allocate unless HALO elides. Custom promise `operator new` to pool frames; ideally hold the `Task_control_block` **inline in the frame** (one alloc for frame+block, not two) so coroutines *reduce* allocs, not add. 
  - **vs senders:** coroutines = ergonomic front-end over the existing `Task`/continuation core; do NOT rebuild the engine on senders. (Senders = separate, larger exploration — see below.)
  - Refs: cppcoro, folly::coro Mutex, TooManyCooks (priority affinity, spawn/fork), Raymond Chen "locks across suspension" series, CppCoreGuidelines #1805.
- **`std::execution` senders (P2300, C++26) — researched (2026-07), SHELVED.** Model: lazy typed *sender* (a recipe advertising `set_value`/`set_error`/`set_stopped` completion signatures) + *receiver* (the callback trio) + `connect`→`operation_state` (immovable, **stack-allocatable, no heap**) + `start`; algorithms (`then`/`when_all`/`bulk`/`on`/`let_value`) compose senders into a compile-time tree that folds into one nested op-state. What it could give **this** project:
  - **Zero-alloc structured composition** — a `then`/`when_all`/`bulk` chain as nested stack op-states, monomorphic, no per-node heap block / type-erasure / refcount. The *structural* answer to 3.1 — but only for the **awaited/structured** subset (fire-and-forget still needs `start_detached`/`async_scope` P3149 + allocator, so not a blanket win).
  - **Env/queries as the `Access_context` carrier — the distinctive angle.** Senders' receiver *environment* (custom queries like `get_access_context(env)`) is the principled channel for context flowing down a chain — a typed, composable replacement for the `thread_local current_access` + snapshot inheritance. Opens (ambitious) **compile-time access checking** (access in the sender's type) or (pragmatic) a cleaner carrier for the runtime harness. This — making the project's *defining feature* typed/composable dataflow — is the one place senders deepen the thesis rather than restyle the API; worth a scoped spike.
  - **Interop + cancellation alignment:** `Scheduler`→`scheduler`, `Task`→`sender` for stdexec ecosystem interop; `bulk` = `parallel_for`; `set_stopped` + env stop-tokens ≈ our cooperative `Cancellation_token` (exceptions-off-friendly).
  - **Tensions (why not wholesale):** clashes with the deliberately **not-templated** monomorphic block (senders are all templates → compile-time + error-message tax); runtime harness vs compile-time dataflow; doesn't fix fire-and-forget allocation; lazy/structured is a different usage model from our eager handle-based tasks; P2300 still settling.
  - **Recommendation:** coroutines first (higher ROI, additive); model the concepts for interop without rebuilding; **prototype access-context-as-env** as the novel spike; do NOT re-found the engine on senders (the monomorphic runtime block earns its keep). Refs: P2300, NVIDIA stdexec, P3149 async_scope.
