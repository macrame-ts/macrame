## Task chaining / results
- **Rename `get()`.** It reads cheap/fast but it *blocks* (and may retract + run a whole subtree inline). Find a name that signals "this can block / do work" — e.g. `wait_get`, `block_get`, `await`(loaded), `sync`, `join`(loaded). Bikeshed later; touches every call site.
- Typed prerequisite -> subsequent chaining (dynamic path): **done** — `Task::then` (single) and `when_all` (multi, results as a tuple).
- Apply-style `when_all`: **done** — `then` unpacks a tuple result into separate continuation args (`then([](A& a, B& b){...})`) when the functor doesn't take the tuple by reference; falls back to the tuple form otherwise.
- `when_all` with void prerequisites and move-only results: **done** — void prerequisites act as pure ordering and drop out of the result (all-void → `Task<void>`); non-void results are carried in a tuple and **moved** (move-only supported). The consumer of a prerequisite's result is `when_all` (results move out), consistent with the single-consumer model.
- Typed chaining in `Static_task_graph` (graph nodes are void-only for now): let a node consume prerequisite-node results.
- `Task`: define get()/then() interaction (currently get() consumes the result; mixing with then() is unsupported). Multiple concurrent blocking `get()` waiters: the monomorphic block waits on a condition variable, so any number of waiters wake (a `Signal` is a barrier); a value `get()` still moves the result, so value tasks stay single-consumer by design.
- Cancellation: **done** — `Cancellation_source`/`token`; cooperative, checked when a task/node is about to run (not-yet-started work is skipped). Cancellation is a completion state that propagates down continuations and graph successors (`Task::is_cancelled()`); `async`/`then`/`execute` take an optional token; a cancelled `void` get() unblocks, a cancelled value get() is fatal (check `is_cancelled()`). A cancelled `when_all` prerequisite cancels the join (it can't form a tuple) instead of stalling — **done**. Cancel *callback* (push notification) — **done**: `Cancel_callback(token, fn)`, RAII/`std::stop_callback`-style; `request_cancel()` fires registered callbacks synchronously (for work that blocks rather than polls). **Body-level early-out** — **done**: a body that declares a trailing `Cancellation_token` parameter (`[](Cancellation_token t)`, or `[](T& v, Cancellation_token t)` for `async`) receives the token so it can poll and early-out for cancellation arriving mid-run; a cooperative return settles **completed** (`Executable::run` forwards `core.token`; `Task_result_t` / `Async_result_t` derive `R` off the token-arity overload, `Async_accessor` keeps the read/write disambiguation working with the extra param). Covers **every** task-body route: `task`/`launch`/`nested`, `async` accessors (read + write), and `then` continuations in all three shapes (void / whole-result / apply-style — `Apply_invocable_tok` / `Invoke_result_tok` extend the detection). A `then` body forwards the continuation's own token (`opts.token`), checked at dispatch too.
- **Task-builder / result-chaining direction** (research, 2026-07): surveyed UE, Taskflow, TBB, HPX, Folly, std::execution, Cilk, GCD, Java CF, .NET, Rust/tokio, Naughty Dog. Findings: a *single-task* configure-then-launch-later builder is the least-used pattern surveyed — where offered (.NET cold `Task`+`Start()`, Rust `task::Builder`) it's avoided; systems fix prereqs *at launch* (UE `Launch(prereqs...)`, tokio `spawn`, ND counters). The *graph* build-then-run(-many) flavor is common and load-bearing (Taskflow, TBB flow graph, senders) — our `Static_task_graph` is squarely in that camp. Result chaining (`.then` typed) is domain-split: essential in server/IO async (Folly/HPX/CF/senders) but with a callback-hell reputation the industry hides behind `async`/`await`; **largely avoided in game engines** (UE has no `.then`, ND uses counters + in-place mutation, blocking `GetResult()` as last resort). Implications: our `ts::task(fn).after(x).launch()` reads as "prereqs-at-launch spelled fluently" (fire-once setup sugar, not a long-lived reconfigurable object), which dodges the discouraged-cold-`Task` objection; **do not** promote it into a persistent reconfigurable builder. `then`/`when_all` typed chaining is a genuine UX nicety but expect real engine use to lean on prerequisite ordering + in-place mutation. Decision on **results-on-`after`**: leaning *no* — result-passing across a prerequisite is `when_all + then` by construction (the producer's result must exist before the dependent's body is fixed), so adding it to `after` re-implements `when_all`; keep the two axes separate (`after` = ordering/cancel propagation; `then`/`when_all` = result flow). Revisit only if a concrete use-case wants a single-result prerequisite feeding one dependent without the tuple.

## Task types
- Unify the handle returned from `Static_task_graph::add_node` with regular async `Task`s: **done** — split, not merged. `add_node` now returns a distinct `Graph_node` (build-time ordering identity: `after`/`before`); `Task<R>` is purely a completion handle (`get`/`then`/`is_done`/`when_all`/`execute`). The run-many model means a node has no single result, so it can't be a single-shot `Task`. Revisit when typed graph chaining lands (a `Graph_node` may then mint a per-run `Task<R>`).
- Reusable tasks: **done** — no new type. `Task_control_block::reset()` re-arms a settled block in place (monomorphic; scalars only — reuse is a block capability, not a result-type concern), and the existing `Task_builder<R>` (from `ts::task(fn)`) is the reusable handle: it already retains the block after `launch()`, and now also has `reset()`/`get()`/`is_done()`. Pattern `t.reset().after(x).launch(); r = t.get();` re-runs one block/body/result-storage across runs (prerequisites re-established each run; one run in flight, `reset()` after the prior settled+consumed, guarded by the block's `ready` flag). `Signal::reset()` falls out (a reusable phase gate). Pooling doesn't help — reuse is the point. Timed-task launch is under Scheduler.

## Control block / allocation
- **Keep `Task_control_block` as small as possible; fuse flags into bits.** Started: `Flags` packs `priority` (2b) + `retractable` (1b) + `run_inline` (1b) into one byte (`priority`/`run_inline` read together at dispatch). Still to audit: `completed`/`cancelled` (bools under the mutex — could be bits), the fn-ptrs (`execute`/`on_complete`), and whether the several vectors can be intrusively linked. A smaller block matters — every task allocates one, on hot paths.
- **Reconsider every `shared_ptr`; prefer intrusive ref-counting.** The block, its `successors`/`prerequisites`/`continuations` vectors, and the public handles are all `std::shared_ptr<Task_control_block>` — each a separate heap control block and an extra atomic per copy. Move to an **intrusive** refcount (a count word in the block itself + a small `Task_ptr` handle): one allocation instead of two, smaller/faster handles, fewer atomics, and the aliasing tricks (`Result_block`/`Executable` wrappers) get simpler. Cross-cutting — do it deliberately, with TSan/ASan coverage.

## Thread_safe / access
- **Standalone public `Pipe`?** Expose the reader/writer pipe as a public serialization primitive (UE's `FPipe`): serialize a stream of tasks without wrapping a single `T`. Open question — does it earn its keep over `Thread_safe<T>`, which *is* a pipe + an owned `T` + access deduction + harness, just friendlier? It only adds value when the serialized resource isn't one wrapped object: several objects that must move in lockstep, external/global state, or pure task-stream ordering. Defer until such a use case shows up; if your resource is one object, `Thread_safe<T>` already covers it.
- `Thread_safe<T>` adopting an **existing** instance (reference/adopt) instead of always constructing T in place. Design ownership/lifetime (borrowed vs owned).
- Pipe FIFO semantics: think hard about whether strict FIFO is the right ordering guarantee, and what it costs.
- Reader/writer prioritisation policy for max throughput (e.g. batch readers vs. favor writers vs. fairness), potentially configurable per `Thread_safe` instance.
- **Dynamic multi-object `async(fn, objs...)`: done** — free function `ts::async(fn, objs...)` (options first: `ts::async({.priority=...}, fn, objs...)`). Per-arg access from the functor's parameter const-ness (`Function_traits`, non-generic lambdas / function pointers). Acquires each object's pipe **mode-aware, in canonical (pipe-address) order, holding** (`multi_acquire` — the same `pipe_acquire`/`pipe_release` primitive as the graph, which shares the address order via its address-sorted `distinct_pipes_`, so nodes and multi-object asyncs can't deadlock against each other), runs `fn(*objs...)` under an `Access_context` declaring all, then releases via a completion continuation (`attach`). Deadlock-free by ordered acquisition (canonical order **with** hold — the standard result; "never incremental" was imprecise). Dedups a repeated object (write-wins). `run_inline` on the options is ignored (multi-object inline is a follow-up); token forwarding to a token-taking body is not supported (arity must match object count). Tests: basic, exclusion vs single-object async, no-deadlock (opposite declared orders), options.
- Deferred / command-buffer write option (read snapshot, apply writes at a sync point) as an alternative to in-place serialized writes.
- Harness: sub-object / region ownership. Currently guards only top-level wrapped systems; a `Body&` handed out by a system isn't covered.
- clang-tidy check enforcing that every public method of a wrapped type calls `TS_CHECK_ACCESS()`.
- Generic-lambda / `auto&` support for access-mode deduction (graph `add_node` currently needs non-generic lambdas so parameter const-ness is introspectable).

## Static_task_graph
- **Per-node mode-aware object acquire (M1.1a): done** — replaced the whole-run writer-only reservation with per-node acquire/release. Each node acquires the objects it touches (in ascending pipe-index / canonical order, holding each — `pipe_acquire`, mode-aware: a reader joins concurrent readers, a writer is exclusive), runs, then releases them at completion (`pipe_release`, mode-aware). So an object is held only over each accessor's `[acquire, complete]` window — **free in the gaps** (a gap node between two accessors leaves it grabbable by async; a late-touched object is free until its node runs), and a read node overlaps a concurrent async read (the old reservation blocked even reads for the whole run). Deadlock-free via canonical order (belt-and-suspenders — edges already serialise conflicting nodes, single-object async can't cycle); canonical order becomes load-bearing when multi-object `async` lands (M1.1 "for async"). Dropped `remaining_objects`/`remaining_accessors`/`object_initiated`/`pipe_accessors_`; `acquire_next` walks the objects. Tests: gap frees object between accessors, reader node overlaps async read.
- **Graph-node inline dispatch (M1.1b): done** — `Graph_node::set_inline()`. When a node's last prerequisite completes on a thread, `acquire_next` acquires the successor's objects on that thread; a `synchronous` flag tracks whether the whole chain stayed there (flipped false on the first `pipe_acquire` deferral). An inline node that stayed synchronous dispatches via the shared `dispatch_ready` trampoline (its block's `run_inline` bit set → inline path, bounded/iterative); otherwise it queues (`run_node`). So an inline node runs on the settling thread only if it acquires all its objects there-and-then; a contended object defers it to the queue — the "revoke predecessor's access, acquire successor's, else defer" hand-off. A chain of inline nodes on one object trampolines (each releases at completion, the next acquires synchronously). Caveats mirror `Task_builder::set_inline`; an all-inline graph runs synchronously on the `execute()` caller. Tests: inline root on caller, inline chain on caller, inline rerun; TSan `graph inline stress` (inline chain contended by async → defer path).
- Nested tasks inside a graph node: **done** — a node runs as a real `Executable` block (`current_task` set, `execution_flag` self-lock), so its body may `ts::nested(...)`; its completion (and thus successors + object release) gates on all nested tasks (§7.1/§8), and nested sub-work inherits the node's `Access_context` by value so it may touch the node's owned guarded data. Enables dynamic, runtime-sized fan-out over a node's store (what a static `parallel_for` can't express). Node blocks + `Run_state` are built at `compile()` and re-armed per run (dispatch via the raw scheduler API; completion via the block's persistent `on_complete` fn-ptr), so a run allocates only its `done` handle — ~19% faster than per-run blocks. Still one run at a time.
- **Object handoff between consecutive same-object accessors: done** — a node no longer releases + re-acquires an object across an edge to the next accessor. In `node_complete`, after collecting the successors this node's completion makes ready, each held object is **handed off** (skip release + skip the successor's re-acquire) when exactly one ready successor takes it in the **same mode** — the pipe state (writer_active / reader count) is then already correct, so the round-trip is pure waste. Unique for a writer (two writers of one object conflict → edge → not both ready). The successor's `acquire_next` skips a handed object via a per-node `preheld` bitmask (position in `pipe_indices`; set before the successor is triggered, so single-writer + happens-before). Otherwise the object is **released** (the M1.1a gap-freeing). The handed object stays held across the edge (no gap), which is fine — the successor just went ready and runs immediately (the eliminated gap is a dispatch-latency micro-window; for a queued successor it's bounded by its queue wait). Works for inline chains (each releases at completion → the next would re-acquire on the same thread — now handed directly) and queued chains alike. Tests: handoff write chain, handoff skips mode change; TSan graph+async stress uses a write→write→write handoff chain contended by async.
- `compile()`: ambiguity detection (two nodes with conflicting access and no explicit order edge) — currently auto-ordered by declaration index.
- Pipelined / concurrent execution (more than one execute() in flight) for frame overlap.
- Profiler-guided graph optimization (reorder/rebucket from measured task durations).

## Fork-join / parallel_for
- Promote a `parallel_for` / fork-join to the core. The sample's `sample/parallel.h` is deadlock-free by having the caller participate (spin-wait), but a core version should use scheduler oversubscription (a standby worker wakes when a task blocks) instead, so a waiting node doesn't tie up a worker. Subtasks must inherit the parent's access context (as the sample's does) so the harness passes.

## Scheduler
- **Task priorities: exposed** — the scheduler always ordered by `Priority {high, normal, low}`; now every queued route threads it to `scheduler.submit`: `ts::launch(fn, token, priority)`, `ts::task(fn).priority(p)`, `Thread_safe::async(fn, token, priority)`, `Graph_node::priority(p)`. Stored on the block (applied at dispatch, incl. prerequisite-gated). `then` now carries priority (and inline) via its `Continuation_options` (`t.then(fn, {.priority = high})`); `when_all`'s join is still bodyless (no priority — its consuming `.then` carries one). **Future — priority propagation:** a task's priority optionally raising its prerequisites/continuations (UE-style).
- **Inline execution mode: done (after/builder path)** — `ts::task(fn).set_inline().after(...).launch()` runs the task on the *settling thread*, not the queue. Dispatch forks in `release` at `num_locks == 0` (`dispatch_ready`): inline → run on this thread, else `submit_ready`. Bounded by a **trampoline** — `Task_control_block::inline_pending` (a thread-local retained-capacity vector) + a head index, drained **FIFO** (advance the index, `clear()` at end; no per-item pop, no steady-state alloc) — so a deep inline chain runs iteratively (O(1) stack; tested to 20k). `run_inline` is a packed bit in `Flags` (with `priority`/`retractable`). Remaining notes:
  - **External-thread execution.** An inline task may run on a thread with no worker context — a `Signal::trigger()` from a UI thread, a retractor. Whatever ambient context our workers rely on (current or future), an externally-run task must either cope with its absence or **detect and fail clearly**. (Not enforced yet.)
  - **Diagnostic — long-running inline tasks** (monopolize the completer, invert priority) and **a `get()` that parks a worker** (generic): detect + warn — future profiling/diagnostics.
  - Scope: `after`/builder path, `then` (via `Continuation_options{.run_inline}`), `async` (via `Async_options{.run_inline}` — `pipe_try_inline`), **and graph nodes** (`Graph_node::set_inline()` — inline on the settling thread when it can acquire its objects synchronously there, else defer; see M1.1b). All four dispatch routes now support inline.
- **Unify continuations, then routes** (roadmap order): (1) inline on the `after` path — **done**. (2) rebase `then` (and `when_all` consumption) onto proper prerequisite tasks — **done**: a `then` continuation is now a real `Executable` with the producer as a `num_locks` prerequisite (queued by default → it gets a priority and the scheduler can slot work between; inline opt-in), its body reading `producer->result_ptr`; a *cancelled* producer still dispatches it (ordering-only), so `Executable::cancel_if` makes it cancel instead of consuming a missing result; deep-retractable via the prerequisite backlink. Retires the inline `then`-callback. (`when_all`'s *join* stays a bodyless aggregator + retraction hint; its *consumption*, the `.then` off it, is the rebased path.) (4) **async inline — done**: `async(fn, {.run_inline = true})` runs the body inline on the calling thread when the pipe is immediately free (`pipe_try_inline`, mode-aware: reader joins as a reader, writer exclusive; never jumps queued work), else enqueues as usual — the opt-in surface is the new `Async_options` aggregate replacing the positional `token`/`priority` params. (3) **static graph node inline — done** (M1.1b): `Graph_node::set_inline()` runs a ready node on the settling thread via the `dispatch_ready` trampoline when it can acquire all its objects synchronously, else defers to the queue; built on M1.1a's per-node acquire. **All four routes (after, then, async, graph) now inline.** See the "task = prerequisites + dispatch-route (scheduler/pipe/inline) + priority" model.
- Spin-then-block hybrid idle (UE-style: spin N cycles, then park on an EventCount) instead of the binary spin/block policy.
- **Per-worker work-stealing deques + lock-free global overflow queue** to replace the single mutex-guarded priority queue (the known scaling bottleneck). **Measured (2026-07, spin idle, submit-only contention sweep):** near-linear to 4 producers (p1 1.86 → p2 3.43 → p4 6.60 M/s) then a hard **plateau at ~6.4 M/s** (p6 6.36, p8 6.17, p12 6.39) — the single queue mutex serializes all submitters, per-op latency floors ~150 ns; adding cores past 4 buys nothing. This is M2. **Research done (2026-07, see the report):** surveyed oneTBB, TooManyCooks (TMC), Chase-Lev, Tokio, Go, Rayon, Cilk, Molecular Matters, Naughty Dog, Vyukov eventcount, and UE `LowLevelTasks` (`LocalQueue.h`/`WaitingQueue.h`/`Scheduler.h`, read on disk). Findings + design:
  - **Verdict on "central high queue + steal the rest":** adopt the *idea* (priority checked first, stealing for the rest) but generalize to the UE/TMC shape — **per-priority queues scanned high→low at every tier** — rather than a one-off central-high special case. No production WS scheduler uses a mutex+`priority_queue`. Make the global queues **lock-free MPMC**; add a **low-starvation valve** (serve low only after N high/normal, à la Go/Tokio's "check global every ~31/61") and a **Go-style spinner cap** (≤ ½ workers searching).
  - **Deque:** Chase-Lev, **bounded + overflow-to-global** (UE/Tokio/Go all bound — avoids the growable-array/ABA reclamation headache), owner LIFO push/take at bottom (cache-hot), thieves FIFO steal at top; Lê-Pop-Cohen-Nardelli C11 memory orderings verbatim (two `seq_cst` fences: one in take, one in steal; push uses a release fence). Worker `submit(normal)` → local deque; non-worker/external `submit` → global (no local deque); high/low → global (promote to per-worker deques later if profiling wants locality). Consider a Tokio/Go **single LIFO/`runnext` slot** for chained wakeups (throttle it — disable-after-3, un-stealable).
  - **Wake:** replace the counting semaphore with a **Vyukov eventcount** over per-worker wait nodes (`prepare_wait`/`commit_wait`/`cancel_wait` + epoch, Dekker seq_cst fence closes the lost-wakeup window; bounded `notify_n` avoids thundering herd). Preserves the block/spin `Idle_policy` (spin = never commit the wait). This is required anyway once tasks sit in local deques (the semaphore can't express "wake this parked worker").
  - **Staged rollout (TSan-gated at the deque step):** (1) replace the single mutex+`priority_queue` with 3 lock-free MPMC queues scanned high→low (keep the semaphore) — removes the comparator-under-one-mutex bottleneck, small verifiable win; (2) eventcount replaces the semaphore; (3) per-worker Chase-Lev deque for normal + steal phase (**the concurrency-critical step — mandatory TSan**); (4) starvation valve + spinner cap; (5) optional per-worker high/low deques.
  - **Platform abstraction (~6 functions):** `park(addr, expected, timeout?)`/`unpark_one`/`unpark_all` (Windows `WaitOnAddress`, Linux `futex`, macOS `__ulock_wait`/`os_sync`; `std::atomic::wait` to start but it lacks **timeout** — needed for standby/oversubscription workers + watchdogs — so plan the swap to raw futex), `thread_spawn`/`set_name`/`set_affinity`, `cpu_count`+minimal `topology`, `cpu_relax`/`yield`. Keep everything else (eventcount, deques, MPMC queues, scheduler loop) portable. Console = fiber backend behind the same `Task` API + core reservation via affinity; mobile = QoS classes + oversubscription/standby over a fixed large pool.
  - **Lower-level thread pool:** keep `std::jthread` for spawn/join, but **replace the semaphore with the eventcount + park/unpark abstraction** (UE's model — per-worker targeted wake + timeouts). Full custom thread creation only later for console fiber backends.
- **Run-on-all-workers**: submit a functor to run once on *every* worker thread (broadcast). Uses: per-thread init/teardown, flushing thread-local state, per-worker warm-up. Needs a way to fan out to N workers and join.
- **Timed / delayed tasks**: "run this in 300ms" — a delay queue (min-heap by fire-time or a timing wheel) that launches a task when due; one-shot vs periodic; cancellable pending timer; interacts with `Reusable_task` (re-arm on a timer).
